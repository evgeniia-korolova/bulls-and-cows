# DESIGN.md

# Архитектура и технические решения

## 1. Структуры данных и алгоритмы

### 1.1. Состояние игры

Для описания состояния игры используются интерфейсы TypeScript и discriminated union.

Основной тип `GameState` объединяет четыре возможных состояния:

- `SetupState` — настройка новой игры;
- `PlayingState` — активная игра;
- `WonState` — игра завершена победой;
- `LostState` — игра завершена досрочно или поражением.

Каждое состояние содержит поле `status` с уникальным строковым значением. Благодаря этому TypeScript может автоматически определять конкретный тип состояния при проверке `status`.

Такой подход позволяет явно описать жизненный цикл игры и не допускать обращения к свойствам, которые недоступны в текущем состоянии.

Например, секретная комбинация `secret` присутствует только в `PlayingState`. В завершённой игре результат хранится отдельно в `GameResult`.

Для настроек используется интерфейс `GameSettings`, содержащий длину комбинации и основание системы счисления. Это позволяет передавать настройки как единый объект, а не использовать несколько несвязанных параметров.

### 1.2. История попыток

История игры представлена массивом объектов `GameAttempt`.

Каждая попытка содержит:

- `guess` — введённую комбинацию;
- `bulls` — количество цифр на правильных позициях;
- `cows` — количество цифр, присутствующих в секрете, но находящихся на других позициях.

В `PlayingState` история хранится в свойстве `history`, а в `GameResult` — в свойстве `attempts`.

Для массивов и свойств интерфейсов используется модификатор `readonly`. Это помогает защитить уже сохранённые данные от случайного изменения и поддерживает иммутабельный подход при обновлении состояния.

При добавлении новой попытки создаётся новый массив, содержащий предыдущую историю и новую запись.

### 1.3. Генерация секретной комбинации — `generateSecret`

Функция создаёт массив допустимых цифр для выбранного основания системы счисления.

Затем на каждой итерации:

1. Случайным образом выбирается индекс доступной цифры.
2. Выбранная цифра добавляется в секретную комбинацию.
3. Цифра удаляется из массива доступных значений.

Таким образом, одна и та же цифра не может попасть в секрет повторно.

Для генерации используется внедряемая функция `random` с `Math.random` в качестве значения по умолчанию. Это позволяет подменять источник случайных чисел при тестировании и получать воспроизводимые результаты.

### 1.4. Оценка попытки — `evaluateGuess`

Функция сравнивает секретную комбинацию с введённой попыткой.

Алгоритм состоит из двух этапов.

**Подсчёт быков:**

Массивы секрета и попытки сравниваются по индексам. Если цифры совпадают на одной позиции, счётчик быков увеличивается.

**Подсчёт коров:**

Сначала из обеих комбинаций исключаются цифры, уже совпавшие по позициям. Затем оставшиеся цифры попытки последовательно ищутся среди оставшихся цифр секрета.

После нахождения совпадения соответствующая цифра удаляется из доступного массива. Это предотвращает повторный подсчёт одной и той же цифры.

В результате функция возвращает объект с количеством быков и коров.

### 1.5. Подсчёт возможных секретов — `countPossibleSecrets`

Количество возможных секретных комбинаций вычисляется рекурсивно.

Поскольку цифры не могут повторяться, для первой позиции доступно `base` вариантов, для второй — `base - 1`, для третьей — `base - 2` и так далее.

Используется рекуррентная формула:

`P(length, base) = base * P(length - 1, base - 1)`

Базовые случаи:

- если `length === 0`, возвращается `1`;
- если `length > base`, возвращается `0`.

Для оптимизации используется мемоизация: результаты сохраняются в `Map`, где ключ формируется из длины комбинации и основания системы счисления.

Если функция повторно вызывается с теми же параметрами, сохранённый результат возвращается без повторных вычислений.

### 1.6. Валидация попытки

Проверка корректности пользовательского ввода разделена на две функции:

- `getGuessValidationError` определяет конкретную причину некорректного ввода;
- `isValidGuess` предоставляет простой булевый результат проверки.

Последовательно проверяются:

1. Соответствие длины комбинации выбранным настройкам.
2. Допустимость каждой цифры для выбранного основания системы счисления.
3. Отсутствие повторяющихся цифр.

Для проверки допустимых символов используется `createDigitValidator`, а для проверки уникальности — структура данных `Set`.

Такое разделение позволяет использовать подробную ошибку при отображении сообщения пользователю и простой результат проверки там, где достаточно значения `boolean`.

## 2. Оценка сложности алгоритмов

Обозначения:

- `n` — длина секретной комбинации;
- `b` — основание системы счисления, то есть количество доступных цифр.

### 2.1. `generateSecret`

**Временная сложность: O(n × b).**

Сначала создаётся массив из `b` доступных цифр — операция занимает O(b).

Затем выполняется `n` итераций. На каждой итерации вызывается `splice`, который может сдвигать оставшиеся элементы массива. В худшем случае это O(b).

Итоговая сложность — O(b + n × b), что упрощается до O(n × b).

### 2.2. `evaluateGuess`

**Временная сложность: O(n²).**

Создание массивов, подсчёт быков и фильтрация оставшихся цифр требуют O(n).

При подсчёте коров используется `reduce`. На каждой итерации вызывается `indexOf`, который в худшем случае просматривает весь массив за O(n). Также создаётся отфильтрованный массив.

Поскольку эта операция может выполняться до `n` раз, общая временная сложность составляет O(n²).

### 2.3. `isValidGuess`

**Временная сложность: O(n × b).**

Функция делегирует проверку `getGuessValidationError`.

Проверка длины занимает O(1).

Создание валидатора формирует массив допустимых цифр за O(b). Затем для каждого символа входной комбинации выполняется проверка через `includes`, которая в худшем случае занимает O(b). Для всей комбинации это O(n × b).

Проверка уникальности с использованием `Set` занимает O(n) в среднем.

Итоговая сложность — O(n × b).

### 2.4. `countPossibleSecrets`

**Временная сложность: O(n) для нового вычисления.**

Функция выполняет один рекурсивный вызов на каждом шаге, уменьшая одновременно `length` и `base`.

Количество вызовов пропорционально длине комбинации. Благодаря мемоизации каждый результат для конкретной пары параметров вычисляется только один раз.

Поэтому одно новое вычисление занимает O(n). Если результат уже находится в `Map`, повторный вызов занимает O(1) в среднем.

**Дополнительная пространственная сложность: O(n)** для стека рекурсии и сохранённых результатов.

## 3. Принципы Clean Code

### 3.1. Single Responsibility Principle — принцип единственной ответственности

Каждая функция отвечает за отдельную задачу.

Примеры:

- `generateSecret` отвечает только за генерацию секретной комбинации.
- `evaluateGuess` отвечает только за оценку введённой попытки.
- `getGuessValidationError` отвечает за определение причины ошибки валидации.
- `isValidGuess` предоставляет результат проверки в формате `boolean`.
- `countPossibleSecrets` отвечает только за подсчёт количества возможных комбинаций.

Разделение задач упрощает тестирование, поддержку и повторное использование функций.

### 3.2. Meaningful Names — осмысленные имена

Имена функций, переменных и интерфейсов отражают их назначение.

Например:

- `availableDigits` — доступные для генерации цифры;
- `remainingSecret` — цифры секрета, ещё не учтённые при сравнении;
- `remainingGuess` — оставшиеся цифры попытки;
- `getGuessValidationError` — получение ошибки валидации;
- `GameAttempt` — отдельная игровая попытка.

Это позволяет понимать назначение кода без дополнительных комментариев.

### 3.3. Small Functions — небольшие функции

Логика разделена на небольшие функции, которые можно проверять независимо.

Например, `isValidGuess` не содержит всей логики валидации, а использует `getGuessValidationError`. В свою очередь, проверка допустимых символов делегирована `createDigitValidator`.

Такой подход уменьшает сложность отдельных функций и облегчает поиск ошибок.

### 3.4. Immutability — неизменяемость данных

Для свойств интерфейсов и массивов используется `readonly`.

При обновлении истории попыток создаётся новый массив, а не изменяется существующий.

Например, добавление новой попытки выполняется через создание массива с предыдущими элементами и новой записью.

Это снижает вероятность случайного изменения состояния и делает обновления более предсказуемыми.

### 3.5. Guard Clauses — ранняя проверка условий

В `generateSecret` входные параметры проверяются в начале функции.

Если длина комбинации или основание системы счисления недопустимы, функция сразу выбрасывает `RangeError`.

В `countPossibleSecrets` базовые случаи рекурсии обрабатываются до основного вычисления.

Это позволяет избежать лишней вложенности условий и делает основной алгоритм понятнее.

### 3.6. DRY — Don't Repeat Yourself

Общая логика проверки допустимых символов вынесена в `createDigitValidator`.

Вместо повторения формирования списка допустимых цифр и проверки каждого символа разные части приложения могут использовать одну функцию-валидатор.

Это уменьшает дублирование кода и позволяет поддерживать единое поведение проверки.

### 3.7. Type Safety — безопасность типов

Для описания настроек, попыток и состояний игры используются отдельные интерфейсы и типы TypeScript.

В `GameState` применяется объединение дискриминируемых типов, позволяющее явно различать состояния игры.

Для допустимых результатов игры используется тип `GameOutcome`, ограничивающий значение строками `won` и `lost`.

Это помогает обнаруживать ошибки на этапе компиляции и уменьшает необходимость в небезопасных преобразованиях типов.

## Заключение

В проекте используются небольшие специализированные функции, явные модели данных, неизменяемые структуры и алгоритмы с предсказуемой сложностью.

Основное внимание уделено разделению ответственности, проверке входных данных, повторному использованию логики и возможности независимого тестирования отдельных частей приложения.
